# Mobile performance — measured 2026-10-31

## Laboratory (Lighthouse 12, mobile emulation, simulated throttling)

Run from a developer machine against production. These are LAB results: a
synthetic load under modelled network and CPU conditions, not what real
visitors experienced.

| Page | Score | LCP | CLS | TBT |
|---|---|---|---|---|
| `/services/maid-service` | 100/100 | 1.8 s | 0 | 0 ms |
| `/cities/san-diego/maid-service` | 99/100 | 1.8 s | 0 | 0 ms |
| `/our-services` | 100/100 | 1.7 s | 0 | 10 ms |

Good thresholds for reference: LCP ≤ 2.5 s, CLS ≤ 0.1, and TBT as the lab
proxy for INP (field INP good is ≤ 200 ms). All three pages sit inside them.

## The finding that changes a decision

**The LCP element is a paragraph of text on every page type, not the
photograph.**

- `/services/maid-service` → `<p class="mt-6 text-sm text-slate-500 leading-relaxed max-w-2xl">`
- `/cities/san-diego/maid-service` → `<p class="mt-3 text-base sm:text-lg text-slate-700 max-w-2xl leading-r`
- `/our-services` → `<p class="mt-3 text-base sm:text-lg text-slate-600">`

This settles something that had only been argued from layout before. The
service photo sits in an aside that stacks below the heading, intro, badges
and buttons on a narrow screen, so it is not the largest contentful paint and
not above the fold. `loading="lazy"` on it is correct, and removing it would
cost bandwidth to prioritise an image no mobile visitor sees first.

**No change to image loading is warranted.** Measured, not assumed.

## Field / real-user data — STILL UNMEASURED

Not available, and this is not the same as "good":

- The PageSpeed Insights API returns `Quota exceeded for quota metric
  'Queries' ... of service 'pagespeedonline.googleapis.com'` for anonymous
  callers, and this machine holds no Google API key.
- CrUX only reports an origin once it has enough real traffic. With no
  completed bookings and a site this new, there may be no field dataset to
  read even with a key.

To close it, either:
1. Add a Google API key and re-run PageSpeed Insights, which returns the CrUX
   field data alongside the lab run; or
2. Read Core Web Vitals in Search Console once the domain is verified — which
   is the same owner action that unblocks the indexing baseline.

## How to re-run

```
export CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
npx --yes lighthouse@12 <url> --quiet --chrome-flags="--headless=new --no-sandbox" \
  --only-categories=performance --form-factor=mobile --screenEmulation.mobile \
  --throttling-method=simulate --output=json --output-path=out.json
```

Raw JSON reports for this run were not committed: they are ~0.5 MB each and
reproducible with the command above.
